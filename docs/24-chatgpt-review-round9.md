# ChatGPT Research Review — Round 9

Date: 2026-09-17

This review evaluates the repository after `23-review-response-round8.md`, focusing on:

- confirmatory versus development-domain logic;
- threshold lineage;
- attack-OOF construction;
- gate-calibration data lineage;
- fair cross-foundation controls;
- routing-policy security;
- interpretation of calibrated probabilities.

## Overall assessment

Round 8 was incorporated carefully.

The method is now stable enough that implementation should begin rather than adding more architecture.

The remaining issues are protocol details that could still invalidate the strongest claims if left implicit.

The most important unresolved problem is now:

\[
\boxed{
\text{the failure label depends on the operational PAD threshold}
}
\]

while OOF risk records are generated from models trained on different source subsets.

Therefore the repository must define exactly how the reference PAD threshold is selected inside every OOF fold and how those fold-specific policies relate to the final deployment policy.

---

# 1. Pilot-target checkpoint selection contradicts the current charter wording

The experiment plan explicitly allows one MICO target to be used as:

> pilot/development target

and allows the finite VLM candidate set to be reduced after pilot evidence.

That is scientifically acceptable if the remaining three targets are treated as confirmatory.

However, the project charter still says:

> Target-domain labels cannot select checkpoints, prompts, thresholds, or hyperparameters.

These two statements cannot both be literally true.

## Recommendation

Change the charter to:

> Confirmatory-target labels cannot select checkpoints, prompts, thresholds, or hyperparameters. One preregistered pilot/development domain may be used for implementation diagnosis and candidate selection, but it is permanently excluded from confirmatory inference.

This is much more precise.

Also change phrases such as:

> before opening any MICO target labels

to:

> before opening any confirmatory MICO target labels

once the development domain has been explicitly designated.

---

# 2. The pilot domain can never later become confirmatory evidence

Stage 4 still says:

> complete four-target MICO.

That is fine for a descriptive benchmark table, but the pilot fold cannot regain confirmatory status merely because the configuration was later frozen.

If target \(A\) was inspected during development, then the unbiased confirmatory estimate is based on:

\[
B,C,D.
\]

## Recommendation

Report two summaries.

### Confirmatory summary

Macro-average only the three untouched targets:

\[
\operatorname{Macro}_{confirm}
=
\frac{1}{3}
\sum_{d\in\{B,C,D\}}
Metric_d.
\]

### Four-target descriptive MICO table

Report all four folds for literature readability, but label the pilot fold:

> development/pilot; not included in confirmatory statistical claim.

Do not combine all four into the primary inferential macro result.

# 3. RQ1 and the charter still name the weaker homogeneous control

The experiment plan correctly promotes:

\[
DINOv2\text{-Reg}+DINOv2
\]

to the strong same-family control required for retaining a cross-foundation title.

However, RQ1 still says that the cross-foundation claim requires advantage over the:

> shared-encoder head-diversity control.

The charter success criterion also still names the shared-encoder control.

This is stale.

## Recommendation

The hierarchy must be identical everywhere.

### Sanity control

\[
DINO_{\text{Reg}}+DINO_{\text{Reg-head2}}.
\]

### Strong same-family confirmatory control

\[
DINO_{\text{Reg}}+DINO_{\text{plain}}.
\]

### Heterogeneous pair

\[
DINO_{\text{Reg}}+VLM.
\]

Only advantage over the **strong same-family representation control** should permit the cross-foundation-specific claim.

# 4. Attack-OOF for SiW-M needs a nested pseudo-attack construction

The protocol now correctly separates domain-OOF from attack-OOF.

However, the phrase:

> hold out attack families according to the official known/held-out split

can still be misread.

Suppose the official test attack is:

\[
A^\star.
\]

Then:

\[
A^\star
\]

must never be used:

- to fit a branch;
- to calibrate branch probabilities;
- to fit the risk gate;
- to choose the gate threshold;
- to select prompts.

Therefore attack-OOF training records cannot be generated by using the final held-out attack itself as an OOF calibration fold.

## Correct construction

Let the known training attacks be:

\[
A_1,A_2,\ldots,A_K
\]

and the final unseen attack be:

\[
A^\star.
\]

Generate pseudo-attack shifts only inside the known set:

\[
A_2,\ldots,A_K
\rightarrow
A_1,
\]

\[
A_1,A_3,\ldots,A_K
\rightarrow
A_2,
\]

and so on.

Concatenate these known-attack OOF records and train the risk gate.

Only then evaluate:

\[
A^\star.
\]

The final unknown attack must remain untouched until final evaluation.

This distinction should be explicit in `04-data-and-protocols.md` and `05-experiment-plan.md`.

# 5. The reference PAD threshold \(\tau_{ref}\) needs a fold-safe definition

The error target is:

\[
e(x)
=
\mathbf 1[
g_{ref}(x)\neq y
]
\]

with:

\[
g_{ref}(x)
=
\mathbf 1[
p_F(x)\ge\tau_{ref}
],
\qquad
p_F(x)
=
\frac{\widehat p_D+\widehat p_V}{2}.
\]

But during domain-OOF or attack-OOF, each fold uses different branch models.

The repository does not yet define how:

\[
\tau_{ref}
\]

is obtained inside each fold.

## Invalid option

Select one threshold using all source domains including the held-out OOF domain.

That leaks held-out labels.

## Leakage-safe option

For OOF fold \(k\), select:

\[
\tau_{ref}^{(k)}
\]

using only the allowed training/calibration remainder of that fold.

But then the risk model is trained on error labels produced under different decision policies:

\[
\tau_{ref}^{(1)},
\tau_{ref}^{(2)},\ldots
\]

while final target inference uses:

\[
\tau_{ref}^{final}.
\]

This policy mismatch must be acknowledged.

## Recommendation

Use fold-specific source-only:

\[
\tau_{ref}^{(k)}
\]

and add the fused decision margin to the risk representation:

\[
m_F(x)
=
p_F(x)-\tau_{ref}^{(k)}.
\]

A simple primary risk vector could become:

\[
z(x)
=
[
\widehat p_D,
\widehat p_V,
d_{abs},
m_F,
q
].
\]

At final inference use:

\[
m_F^{target}
=
p_F-\tau_{ref}^{final}.
\]

This gives the gate an explicit policy-relative coordinate and makes risk features comparable across fold-specific operating thresholds.

If the project wants to keep the current risk vector unchanged, then it should instead preregister one truly fixed common threshold and justify why it applies across all folds.

# 6. Add a decision-margin uncertainty baseline

The current risk baselines include:

- MSP;
- entropy;
- disagreement;
- Mahalanobis.

But the operational decision threshold may not be:

\[
0.5.
\]

Under a low-APCER policy, the relevant confidence quantity is often distance from the actual decision boundary:

\[
u_{margin}(x)
=
-
|
p_F(x)-\tau_{ref}
|.
\]

A sample can have low entropy around \(p=0.8\) but still lie near an operational threshold such as:

\[
\tau_{ref}=0.82.
\]

Therefore fused entropy/MSP may be poorly aligned with the actual security decision.

## Required baseline

Add:

\[
\boxed{
|p_F-\tau_{ref}|
}
\]

or its negative as a failure-risk score.

Also consider branch-specific operational margins as secondary baselines.

This is one of the strongest simple uncertainty baselines for a thresholded security classifier.

---

# 7. The permanent gate-calibration set \(G\) must be stratified and sufficiently informative

Round 8 correctly makes \(G\) completely out of sample.

However, threshold selection can still be unstable if \(G\) contains:

- too few attacks;
- too few branch/fusion failures;
- poor domain balance;
- no difficult samples.

## Recommendation

Define \(G\) before target evaluation with stratification by at least:

- source domain;
- bona-fide/attack;
- attack family where possible.

Report:

\[
N_G,
\]

\[
N_{G,attack},
\]

\[
N_{G,error},
\]

and the number of false accepts available for gate-threshold selection.

If \(G\) is too small to identify the desired operating point with useful confidence, do not pretend the threshold is statistically stable.

This is analogous to the finite-sample APCER issue already recognized elsewhere.

---

# 8. Holding out \(G\) changes fairness against published MICO baselines

The strict selective protocol permanently excludes \(G\) from branch training.

That is excellent for leakage control.

But most published MICO baselines train using all allowed source training data.

Therefore a direct accuracy comparison can disadvantage the proposed method simply because it uses less source supervision.

## Recommendation

Separate two purposes.

### Strict selective-method track

All internal baselines and controls use the exact same reduced source data:

\[
Source\setminus G.
\]

This is the primary fair test of the proposed risk mechanism.

### Literature-compatible branch track

Optionally train branch-only models using the conventional full source data to show where DINO/VLM performance lies relative to existing MICO literature.

Do not compare a full-data external baseline against a reduced-data proposed branch and interpret the difference as architectural.

If the paper later needs maximum source-data efficiency, fully cross-fitted threshold calibration can be explored as a secondary extension.

# 9. Heterogeneity advantage is still confounded by second-branch standalone strength

The paired heterogeneity metric is now:

\[
\Delta_{hetero}
=
FARR(DINO,VLM)
-
FARR(DINO,DINO_2).
\]

Pairing is correct.

However, a positive result can occur simply because:

\[
VLM
\]

is a much stronger second classifier than:

\[
DINO_2.
\]

That is not necessarily evidence that heterogeneous pretraining produces more complementary errors.

## Recommendation

In addition to raw rescue, report a complementarity lift.

For general DINO failures:

\[
Lift_{REF}(B)
=
P(B\ correct\mid DINO\ wrong)
-
P(B\ correct).
\]

For security-critical attack errors:

\[
Lift_{FA}(B)
=
P(B\ blocks\mid DINO\ false\ accept)
-
P(B\ blocks\mid y=attack).
\]

Then compare:

\[
Lift_{FA}(VLM)
\]

against:

\[
Lift_{FA}(DINO_2).
\]

A positive rescue rate says the second model is useful.

A positive complementarity lift says it is especially useful **where the primary model fails**.

This makes the cross-foundation argument much stronger.

# 10. Define the metric behind \(\Delta_{CF}\) and \(\Delta_{dis}\)

RQ2 now correctly defines:

\[
\Delta_{CF}
=
Perf(R_{DV})
-
\max(
Perf(R_D),Perf(R_V)
)
\]

and:

\[
\Delta_{dis}
=
Perf(R_{DVd})
-
Perf(R_{DV}).
\]

But:

\[
Perf(\cdot)
\]

is not defined.

If the paper allows `Perf` to mean whichever of:

- error AUPR;
- AUROC;
- excess-AURC;
- class-aware AURC;

looks best after target evaluation, the preregistration loses value.

## Recommendation

Define a primary metric now.

For example:

\[
Perf_{primary}
=
AUPR_{\text{error}}.
\]

Then:

\[
\Delta_{CF}^{AUPR}
\]

and:

\[
\Delta_{dis}^{AUPR}
\]

are the primary claim quantities.

Use excess-AURC and class-conditional metrics as mandatory supporting endpoints.

Alternatively, if selective deployment is the true central contribution, choose excess-AURC as primary.

But choose one before confirmatory evaluation.

# 11. "Calibrated probability" is not automatically a real-world posterior probability

Branch calibration is fitted on research datasets with artificial sampling and dataset-specific class prevalence.

Even with affine logistic calibration:

\[
\widehat p
=
\sigma(a\ell+b),
\]

the resulting number is calibrated to the source evaluation distribution, not necessarily to the real deployment prevalence of attacks.

Therefore statements such as:

> probability that this input is a spoof

should be used cautiously.

## Recommendation

Use language such as:

> source-calibrated PAD probability/score

unless deployment priors are explicitly modeled.

Also define class weighting in the calibration objective.

The repository already defines equal **domain** weighting, but not whether each domain uses:

- its natural bona-fide/attack prevalence;
- class-balanced calibration loss.

This matters because the intercept:

\[
b
\]

depends on class prevalence.

A reproducible policy could be:

1. compute calibration loss separately per domain;
2. class-balance within each domain;
3. average domains equally.

If this is chosen, acknowledge that the output is a standardized source-calibrated score rather than a deployment posterior.

# 12. Routing-gate selection is now the least specified fitted component

The post-VLM risk gate is heavily specified.

The pre-VLM routing gate is still described broadly as:

> DINO confidence and image quality decide whether to accept directly or invoke the VLM.

But the routing policy has:

- features;
- thresholds;
- optimization objective;
- security consequences.

These need the same source-only discipline as the selective gate.

## Recommendation

Specify:

\[
R(x)
\in
\{
\text{early exit},
\text{invoke VLM}
\}.
\]

Preregister:

- routing score;
- threshold selection data;
- security constraint;
- whether image-quality terms are used.

Do not tune the routing threshold on confirmatory targets.

---

# 13. The safest primary routing policy is early reject, not early accept

Security-asymmetric routing is a good idea.

For PAD, the most conservative primary policy is:

```text
DINO confidently SPOOF
    -> early non-accept

everything else
    -> invoke VLM
```

This saves VLM compute on obvious attacks without creating a new attack-acceptance path.

By contrast:

```text
DINO confidently LIVE
    -> direct accept
```

can bypass the very cross-foundation check that is supposed to rescue DINO false accepts.

## Recommendation

Make:

\[
\boxed{
\text{spoof-only early exit}
}
\]

the primary conditional policy.

Treat direct-live acceptance as an ablation requiring its own source-selected false-accept bound.

This makes the security story cleaner and easier to defend.

---

# 14. End-to-end system evaluation must account for the routing path explicitly

The Stage-2 risk estimator applies after VLM invocation.

But the Stage-3 conditional system contains two types of transactions:

### Direct DINO exits

No VLM disagreement exists.

### VLM-invoked transactions

The full:

\[
g_{ref}
+
r_{err}
\]

pipeline applies.

Therefore the final system cannot be evaluated as if every transaction had a cross-foundation risk score.

## Recommendation

Report route-specific counts:

\[
N_{\text{direct-DINO}},
\]

\[
N_{\text{VLM-invoked}},
\]

and route-specific:

- false accepts;
- bona-fide non-accepts;
- detector failures;
- abstentions.

Then report end-to-end totals over the original transaction denominator.

This prevents a routing policy from hiding difficult samples in one branch of the pipeline.

# 17. "Source-only" needs precise wording after pilot-based model selection

Once a pilot target is used to choose the VLM checkpoint, the final global configuration is no longer purely source-only with respect to the entire four-domain MICO universe.

It is still source-only with respect to the three untouched confirmatory targets.

Therefore the strongest precise statement is:

> The risk calibration and decision thresholds are source-only for every evaluated confirmatory target; one preregistered development domain is used for global architecture/checkpoint selection and excluded from confirmatory inference.

This is still a strong design.

It is simply more accurate than saying the entire research pipeline used no target-domain labels at any point.

# 18. The Stage-1 stopping logic should use realized rescue for continuation

The plan now reports both:

\[
FARR_{VLM}
\]

and:

\[
FARR_g.
\]

This is correct.

For continuing to Stage 2, the more relevant system-level criterion is:

\[
FARR_g.
\]

A VLM that potentially rescues DINO failures but whose fixed source-selected fusion cannot exploit them is not yet evidence for the proposed selective system.

Therefore:

### diagnostic evidence

\[
FARR_{VLM}
\]

shows information exists.

### project continuation evidence

\[
FARR_g
\]

shows the fixed source-only system can use it.

The current Level-1 criterion already moves in this direction; retain that distinction consistently throughout the manuscript.

# Final recommendation

The project is ready to implement Stage 1.

The architecture should not be expanded further.

At this point the most important work is to make every threshold and every dataset role traceable.

The key implementation invariant should be:

\[
\boxed{
\text{every label used for training, calibration, threshold selection, or model selection has one explicit role}
}
\]

and no confirmatory target label may influence any earlier role.

For Stage 1, the evidence chain should be:

\[
\text{DINO failure}
\rightarrow
\text{VLM potential rescue}
\rightarrow
\text{fixed fusion realized rescue}
\rightarrow
\text{paired advantage over strong same-family diversity}.
\]

For Stage 2, the critical additional distinction is:

\[
\boxed{
\text{prediction confidence relative to the actual operational threshold}
}
\]

rather than generic softmax confidence around 0.5.

If the project resolves threshold lineage, attack-OOF nesting, and pilot/confirmatory status cleanly, the protocol becomes substantially harder for a reviewer to attack than the original proposal.
